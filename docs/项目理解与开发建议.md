# 项目定位理解

本项目定位为面向高校新生的 3D 虚拟校园体验平台，核心不是传统校园官网或二维导览，而是让新生在正式入学前，通过虚拟角色进入一个可探索、可问答、可互动的校园空间。

产品的关键价值有三点：

- 降低新生对校园环境、建筑位置、生活区域的陌生感。
- 通过 AI NPC 把分散在官网、新生手册、学院介绍中的信息变成可对话的校园助手。
- 用轻量社交和反馈机制验证新生是否愿意在入学前通过虚拟校园建立熟悉感和参与感。

因此，Alpha / MVP 阶段的产品目标应优先验证“3D 探索 + AI 校园问答”是否成立，社交、任务、成就、个人空间等能力应作为后续增强项。

# 核心用户流程理解

文档中的核心用户路径可以理解为一个最短体验闭环：

1. 新生进入平台。
2. 注册或登录，填写昵称、头像、专业、入学年份、兴趣标签等基础身份信息。
3. 创建虚拟角色，MVP 阶段使用固定 Avatar 模板。
4. 从校园入口进入 3D 虚拟校园。
5. 控制角色移动，探索教学楼、图书馆、食堂、宿舍等关键区域。
6. 接近建筑后查看建筑介绍、位置说明、图片或相关信息。
7. 与 AI NPC 对话，询问报到流程、食堂、宿舍、专业、校园规则等问题。
8. 查看其他新生信息，产生基础互动。
9. 提交评分和反馈，为后续产品优化提供依据。

从产品验证角度看，真正必须闭合的是：

进入校园 -> 探索建筑 -> 询问 AI NPC -> 提交反馈。

用户注册、角色创建、社交互动都可以做轻量化处理，避免 Alpha 阶段被账号体系和多人同步复杂度拖住。

# MVP功能范围

当前文档定义的 P0 功能包括：

- 用户登录
- 创建角色
- 3D 校园地图
- 玩家移动
- 建筑查看
- AI NPC
- 校园 RAG 问答
- 用户反馈

这个范围方向正确，但一个月内仍然偏大，尤其是同时包含 3D 场景、后端用户系统、AI Agent、RAG、部署和可展示 Demo。建议将 Alpha MVP 收敛为：

- 必须完成：3D 场景基础漫游、关键建筑点位、建筑信息弹窗、单个 AI 学长 NPC、基础 RAG 问答、反馈提交。
- 简化完成：用户身份创建可先做昵称 + 专业 + 兴趣，不必完整认证体系。
- 暂缓完成：好友系统、私聊、附近用户实时同步、复杂 Avatar 自定义、任务/成就/个人空间、多 NPC 差异化 Agent。

建议 Alpha 的验收标准聚焦在：

- 用户能在浏览器中进入 3D 校园。
- 用户能用键盘和鼠标完成基本移动与视角控制。
- 用户能查看至少 4 类核心建筑信息。
- 用户能向 AI NPC 提问，并得到基于校园知识库的回答。
- 系统能记录用户反馈和基本行为指标。

# 技术架构理解

当前设计采用前后端分离和 AI 服务独立的架构：

- 前端：Vue3 + TypeScript + Three.js + WebGL，负责页面 UI、3D 场景渲染、玩家控制、建筑和 NPC 交互。
- 后端：Spring Boot + PostgreSQL + Redis + WebSocket，负责用户、角色、建筑、反馈、社交和实时状态。
- AI 服务：FastAPI + LangGraph + RAG + pgvector，负责 NPC 对话、知识库检索和回答生成。
- 数据库：PostgreSQL 存储核心业务数据，Redis 存储在线状态和实时位置，pgvector 存储校园知识向量。
- 部署：Docker + Nginx，统一前端、后端、AI 服务和数据库部署。

架构方向总体合理。Three.js 不直接访问 AI 服务，而是通过 Spring Boot 业务层转发到 FastAPI AI 服务，这个边界是正确的：前端保持轻，业务权限、用户身份、日志、限流、对话记录都可以在后端统一治理。

数据设计中，MVP 核心表可以先保留：

- user
- avatar
- building
- npc
- chat_history
- feedback
- knowledge_document

friend、message、campus_area、task 可以延后。

# 当前风险分析

功能范围风险：

当前 MVP 同时包含 3D 漫游、AI NPC、RAG、用户系统、多人社交、WebSocket、部署和展示材料。对一个月周期来说，范围偏大。真正高风险的是 3D 资产质量、AI 知识库质量、多人同步和聊天系统，如果全部并行推进，容易出现每个模块都有 Demo 但整体体验不顺。

技术方案风险：

技术选型本身合理，但栈较重。Vue3 + Three.js、Spring Boot、FastAPI、LangGraph、PostgreSQL、Redis、pgvector、Docker 全部引入，会增加联调成本。Alpha 阶段应减少“完整工程化”的欲望，优先保证体验链路跑通。

一个月可完成性风险：

如果按文档中的完整 MVP 交付，包括好友系统、聊天、附近用户、行为记录、部署和 Demo 视频，一个月完成风险较高。若收缩为“单人 3D 探索 + 单 AI NPC + 建筑信息 + 反馈”，一个月可完成性明显提高。

3D 资产风险：

3D 校园体验的质量高度依赖模型资源。如果没有现成 GLB/GLTF 校园模型，手工建模会成为最大时间黑洞。建议 Alpha 使用低多边形占位建筑、真实名称和准确点位，先验证体验，不追求高拟真。

AI 质量风险：

RAG 的价值取决于知识文档质量、切片策略、检索效果和提示词约束。如果校园资料不足或格式混乱，AI NPC 容易回答泛化、幻觉或不稳定。Alpha 应先准备少量高质量知识文档，而不是追求知识库规模。

实时社交风险：

附近用户、位置同步、好友和聊天会引入 WebSocket、在线状态、消息一致性和隐私问题。它们对验证“新生是否喜欢 3D AI 校园”不是第一优先级，建议从 P0 下移到 P1。

数据设计风险：

`user` 是数据库保留语义较强的名称，实际落库建议使用 `users` 或 `app_user`。另外 `campus_area.boundary` 依赖 PostGIS，MVP 可以不引入，避免额外数据库扩展和空间数据处理成本。

架构边界风险：

文档中数据流写到“用户移动 -> Spring Boot 保存状态 -> 其他服务同步”。如果每次移动都持久化到 PostgreSQL，会造成不必要压力。玩家实时坐标应优先放 Redis 或仅前端本地，退出或关键节点再保存。

# 开发建议

建议将 Alpha 明确拆成“可体验主线”和“可延后增强”。

Alpha 必做主线：

1. 浏览器打开后进入 3D 校园场景。
2. 用户选择或创建一个简单身份。
3. 用户控制角色移动，能看到校园入口、教学楼、图书馆、食堂、宿舍等核心建筑。
4. 用户点击或靠近建筑后看到建筑信息。
5. 用户与一个 AI 学长 NPC 对话。
6. AI 回答来自校园知识库，回答不足时明确说明信息有限。
7. 用户提交体验反馈。

建议暂缓：

- 完整注册登录和复杂权限。
- 多人实时位置同步。
- 好友系统。
- 私聊系统。
- 多 NPC 个性化 Agent。
- 任务、成就、个人空间。
- PostGIS 空间区域。
- 高拟真校园模型。

技术实现建议：

- 前端先用简单几何体或轻量 GLB 表示建筑，保证移动、碰撞边界、点击交互和 UI 流程稳定。
- 建筑数据先由后端接口或静态 JSON 提供，字段保持和未来 building 表一致。
- AI 服务先做单 NPC、单流程：问题 -> 检索 -> 回答 -> 保存记录。LangGraph 可以保留，但不要过早设计复杂多工具 Agent。
- 向量库建议优先使用 pgvector，减少 Chroma 与 PostgreSQL 双知识库维护成本。
- Redis 只在真正做多人在线时引入；如果 Alpha 不做实时社交，可暂时不用 Redis。
- WebSocket 放到 P1；Alpha 用普通 HTTP 完成 AI 对话和反馈即可。
- 反馈系统必须保留，因为它直接服务 MVP 验证目标。

一个月开发节奏建议：

- 第 1 周：跑通前端 3D 场景、基础移动、建筑占位和建筑信息展示。
- 第 2 周：跑通后端基础数据接口、反馈接口、AI 服务 Demo。
- 第 3 周：接入 RAG 知识库，打磨 AI 学长问答质量，完成前后端联调。
- 第 4 周：优化 UI、性能、部署和演示材料，修复主流程问题。

最终建议：

本项目愿景可以保留“3D 校园 + AI Agent + 新生社交”，但 Alpha 阶段应该只证明一件事：新生是否愿意在 3D 校园里主动探索，并通过 AI NPC 获得有用信息。只要这个闭环成立，再扩展多人社交和游戏化才有意义。
